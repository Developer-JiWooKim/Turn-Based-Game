구조

계층 분리를 컴파일러에게 맡긴다

“전투 로직을 MonoBehaviour에 두지 않는다”는 규칙은 합의로 두면 시간이 지나며 무너집니다. 어셈블리 정의로 다섯 계층을 나누고, 최하단 Game.Core에 noEngineReferences를 걸어 규칙을 어긴 코드가 빌드되지 않게 했습니다.

이 한 줄 때문에 Game.Core 안에서는 UnityEngine을 using조차 할 수 없습니다. 순수 C# 유지가 의지가 아니라 빌드 조건이 되고, Core 단위 테스트를 붙일 때의 전제조건도 함께 해결됩니다.

계층은 위로만 참조합니다. Game.View는 아래 넷을 전부 알지만 Game.Core는 자신이 게임 엔진 위에서 돈다는 사실조차 모릅니다. 폴더가 떨어져 있는 UI/·Audio/는 .asmref로 각 어셈블리에 합류시켰습니다.

배치 규칙에서 한 번 걸린 적이 있습니다. FadeScreenEffect를 처음에 UI/에 뒀는데 GameManager가 이걸 참조하면서 Systems ↔ UI 순환 참조가 났습니다. UI가 아니라 Systems/에 있어야 할 코드였습니다 — 계층을 강제하니 배치가 틀렸다는 사실이 컴파일 시점에 드러났습니다.

전투 코어

세 곳에서만 멈추는 턴 루프

전투 진행은 BattleSimulation.RunAsync 하나가 끝까지 돌립니다. 여기서의 await는 시간이 흐르기를 기다리는 게 아니라 바깥이 끝났다고 알려주기를 기다립니다. 멈추는 지점은 셋뿐입니다 — 플레이어 입력, 연출 완료, 퍼즈 해제. 구독자가 아무것도 등록하지 않으면 모든 대기가 즉시 통과해 전투가 연출 없이 끝까지 돌아갑니다.

강조된 세 줄이 전부입니다. 결과를 먼저 확정하고 연출은 그 뒤에 재생하기 때문에, 애니메이션이 느리거나 아예 재생되지 않아도 전투 결과가 달라지지 않습니다.

await 뒤의 상태를 다시 확인해야 한다

턴 순서는 턴 시작 시점의 스냅샷이라, 앞선 유닛의 공격으로 뒤 순번이 이미 죽어 있을 수 있습니다. 생존·종료 검사를 await보다 뒤에 둔 이유입니다 — 기다리는 사이에 상태가 바뀝니다.

취소 확인 위치도 같은 이유로 옮겼습니다. 처음엔 턴 시작 지점에서만 확인했는데, 그러면 플레이어 차례에 ‘배틀 중단’을 눌러도 이번 턴의 남은 몬스터 행동이 전부 끝난 뒤에야 결과 화면으로 넘어갔습니다. 지금은 매 유닛 행동 직전에 확인합니다.

연출을 기다리게 하는 방법 — Core는 Unity를 모른다

Game.Core는 코루틴도 Awaitable도 모릅니다. 그래서 “기다린다”를 구독자가 Task를 등록하는 방식으로 뒤집었습니다. 이벤트 인자가 Task 목록을 들고 있고, 시뮬레이션은 등록된 것만 기다립니다.

View 쪽(BattlePresenter)이 ActionResolved를 구독해 자신의 연출 Task를 RegisterPlayback으로 넣습니다. 등록이 없으면 Task.CompletedTask라 전투가 그냥 흘러갑니다 — 연출 없이도 성립하는 구조라 로직만 따로 돌려볼 수 있습니다.

같은 이유로 퍼즈도 순수 인터페이스(IPauseGate) 한 개입니다. 구현은 View의 BattlePausePanel이 하고, Core는 WaitWhilePausedAsync만 압니다. Time.timeScale은 쓰지 않았습니다 — 연출 대기(Awaitable.WaitForSecondsAsync)가 timeScale에 영향받는지 보장되지 않아 애니메이션만 얼고 시뮬레이션은 계속 도는 위험이 있고, 씬 전환 페이드도 같은 Awaitable 기반이라 함께 멈출 수 있습니다.

반복되던 TCS 패턴을 한 타입으로

플레이어 타겟 입력, 선택지 카드 클릭, 결과 화면 확인 — 전부 “TaskCompletionSource 생성 → 취소 토큰 연결 → await → 정리”라 매번 손으로 쓰면 두 가지를 빠뜨리기 쉽습니다. RunContinuationsAsynchronously(없으면 완료를 알리는 쪽 스레드에서 이어지는 코드가 그대로 실행됨)와 ct.Register 해제(없으면 토큰에 콜백이 쌓임)입니다.

BattlePausePanel만 일부러 이걸 쓰지 않습니다. 그쪽은 신호를 여는 주체(퍼즈)와 기다리는 주체(시뮬레이션)가 달라 소유 모델이 반대라, 억지로 맞추면 오히려 읽기 어려워집니다.

성능

끝이 없는 게임이라 할당이 쌓인다

스테이지에 끝이 없으므로 “한 번에 큰 비용”보다 “매 행동마다 조금씩 쌓이는 비용”이 문제입니다. 대상 후보 조회처럼 모든 유닛의 모든 행동마다 불리는 경로부터 손봤습니다.

LINQ 대신 직접 루프를 쓰고 리스트를 재사용합니다. 대신 호출자가 즉시 소비해야 한다는 제약이 생기므로, 결과를 await 너머로 들고 가는 두 곳(PlayerActionSelector와 라인 스킬)은 자체 리스트로 복사합니다. 전투 종료 시 생존자 목록도 BattleDirector가 런 데이터에 반영할 때까지 들고 있으므로 여기만 새 리스트입니다.

같은 추첨기를 두 개로 나눈 이유

가중치 버퍼(_weights)도 셀렉터가 필드로 들고 재사용합니다. 후보 목록이 곧 생존자라 전열이 쓰러지면 남은 유닛끼리 자동으로 재정규화됩니다 — 별도 처리가 없습니다.

유닛 View는 파괴하지 않는다

유닛 인스턴스를 프리팹 단위 ObjectPool에 반납·재사용합니다. 무한 타워에서 스테이지마다 생성·파괴하면 그 비용이 계속 쌓이기 때문입니다.

풀링에서 실제로 걸렸던 함정입니다. 처음엔 스폰마다 레이어를 다시 캐싱했는데, 겨냥 하이라이트가 켜진 상태로 반납된 인스턴스를 재사용하면 하이라이트 레이어가 “원래 레이어”로 굳어 그 유닛만 영영 빨갛게 남았습니다. 체력바도 같은 성격의 버그가 있어서, 사망 시 숨긴 것을 Initialize에서 되살리고 게이지는 연출 없이 즉시 대입합니다 — 연출을 쓰면 이전 전투의 잔량에서 스르륵 차오릅니다.

실수 방지

런타임에 드러날 실수를 앞당기기

혼자 만들면 리뷰어가 없으니, 자주 반복한 실수는 코드가 대신 막게 만들었습니다. 가능하면 컴파일 에러로, 안 되면 시작 즉시 로그로 옮깁니다.

잘못된 API 사용을 컴파일 에러로

null 보고를 공용 헬퍼로 모으면서 메서드를 값의 출처별로 나눴습니다 — 인스펙터 참조인지, 런타임 조회 결과인지, 순수 C# 참조인지에 따라 로그를 읽는 사람이 뒤져야 할 곳이 다르기 때문입니다. 문제는 UnityEngine.Object를 순수 C#용 메서드에 넘기는 실수였습니다. 일반 object로 받으면 Unity의 == 오버로드가 사라져 이미 파괴된 객체가 null이 아닌 것으로 통과합니다.

로그 접두어는 문자열이 아니라 owner.GetType().Name에서 뽑습니다 — 예전에 메시지를 복사·붙여넣다 다른 클래스 이름이 남아 엉뚱한 파일을 뒤진 적이 있어서입니다. 반환값을 hasError |= …로 누적해 빠진 참조를 한 번에 모두 보고합니다(하나 고치면 또 걸리는 식이 되지 않도록).

조용히 실행되지 않는 코드 막기

Unity는 같은 이름의 메시지가 파생 클래스에도 있으면 파생 쪽만 호출합니다. 베이스의 private void Start()는 컴파일러가 hides 경고조차 내지 않고 조용히 실행되지 않습니다 — 패널 하나만 번역이 통째로 안 되는 함정이었습니다.

BindButton이 따로 있는 이유는 Root.Q<Button>("x").clicked += …가 요소를 못 찾으면 그 줄에서 NullReferenceException이 나 패널 전체의 배선이 통째로 끊기기 때문입니다. UXML 이름 오타는 인스펙터 검증으로도 OnValidate로도 잡히지 않고(트리가 런타임에만 존재합니다) 화면이 조용히 비는 것으로만 드러나므로, 1회 대입 지점에서 즉시 로그를 남깁니다.

같은 문자열이 두 곳에 적히지 않게

액션 경로가 InputManager와 키설정 UI 양쪽에 따로 적혀 있어서, 한쪽만 고치면 키 설정 화면만 조용히 망가졌습니다(버튼에 -가 뜨고 눌러도 무반응). 상수를 한 파일로 모아 두 곳이 같은 값을 쓰게 했습니다.

컴파일러가 에셋과 대조해주지는 않으므로, 액션 캐싱은 throwIfNotFound: true로 시작 즉시 터뜨리고 리바인딩 경로는 로그를 남깁니다. Label이 표시 문자열이 아니라 번역 키(ui.keybind.*)인 것도 같은 이유입니다 — 표시는 표시하는 쪽이 합니다.

코드 구성

파일이 어디에 있는가

“바뀌는 이유가 다르면 파일도 나눈다”를 기준으로 삼았습니다. BattlePresenter가 532줄이 됐을 때, “Core 이벤트를 화면 어디에 반영할지”와 “한 번의 행동을 어떻게 보여줄지”를 갈라 ActionPlayback(246줄)으로 떼어냈습니다 — HUD 표기를 바꿀 때와 연출 타이밍을 조정할 때 손대는 파일이 달라집니다.

ActionPlayback을 분리할 때 MonoBehaviour로 만들지 않은 것이 중요했습니다. 컴포넌트로 쪼갰다면 인스펙터 슬롯이 새 오브젝트로 흩어져 씬 배선을 다시 해야 했습니다. 연출 참조 5종은 기존 [SerializeField]에 그대로 두고 Initialize에서 생성자로 넘겨, 에디터 작업 없이 코드만 분리했습니다.

레지스트리 같은 공용 객체는 BattleDirector만 인스펙터로 들고 나머지 넷은 Initialize 주입으로 받습니다 — 인스펙터 슬롯을 중복으로 두면 서로 다른 오브젝트를 가리켜도 알아챌 방법이 없기 때문입니다. 최근 전체 스캔에서 미사용 public 메서드 0개, 미사용 [SerializeField] 0개를 확인했습니다.

고치는 데 오래 걸린 버그는 대개 어려워서가 아니라 증상이 엉뚱한 곳을 가리켜서였습니다. 다시 같은 곳을 뒤지지 않도록 원인까지 코드 주석과 문서에 남겼습니다.

적이 공격하는 동안 ‘배틀 중단’ 버튼이 먹지 않는 것처럼 보였다
시뮬레이션의 await 중 취소 토큰을 받지 않는 것은 연출 대기(WhenPlaybackComplete) 하나뿐이었습니다. 그래서 그 행동이 끝난 뒤에야 중단이 반영됐습니다. 잠금 조건을 “퍼즈 중”이 아니라 “연출 재생 중”으로 잡아 버튼을 비활성화하고, Update에서 매 프레임 확인해 연출이 끝나는 순간 풀리게 했습니다 — 플레이어 차례와 게이트 대기는 토큰을 받아 즉시 중단되므로 잠그면 안 됩니다.
1번 자리에 선 캐릭터와 1번 교체 카드가 서로 다른 사람이었다
교체 대상 카드를 RunData.Members 순서로 만들었는데 그건 영입 순서였습니다. 화면은 슬롯 순서이고, 스폰은 앞쪽 빈자리를 재사용하는 반면 영입은 리스트 끝에 붙습니다. 추방으로 중간 슬롯이 빈 뒤 영입하면 두 순서가 갈라집니다. 레지스트리가 돌려주는 슬롯 순서를 쓰고, 멤버와 배치 라벨을 한 struct로 묶어 돌려주게 바꿨습니다.
기절한 아군 차례에 “당신의 차례” 프롬프트가 뜬 채 입력이 먹지 않았다
상태이상 처리를 ActorTurnStarted 뒤에 두면, 기절해서 건너뛸 유닛에게도 차례를 먼저 알리게 됩니다. 순서를 뒤집어 해결했습니다. 같은 메서드 안에서 기절 여부를 지속 턴 감소보다 먼저 읽는 것도 규칙입니다 — 뒤로 미루면 1턴짜리 기절이 아무 행동도 막지 못한 채 사라집니다.
총구 섬광 이펙트가 아예 보이지 않았다
풀링한 ParticleSystem을 Play()와 같은 프레임에 Stop() 하면 입자가 하나도 방출되지 않습니다. 투사체는 도착 후 반납이라 괜찮았지만 총구 섬광은 스폰 직후여서 걸렸습니다. 반납 시 방출 중지는 여러 프레임 재생된 뒤에만 켜도록 했습니다.
디버프 지속 턴 표기가 부여 시점 값에서 멈춰 있었다
StatusChanged를 부여·저항·만료에만 발생시켰기 때문입니다. 지속 턴이 줄 때마다도 알려야 표기가 따라옵니다. 다만 상태 개수만큼 보내면 이벤트가 불필요하게 늘어나므로, View가 목록 전체를 다시 읽는 것을 전제로 유닛당 1회만 보냅니다.
캐릭터 선택에서 방향키를 누르고 Enter를 치면 엉뚱한 버튼이 눌렸다
방향키·확정을 직접 처리하면서 EventSystem의 내장 UI 네비게이션도 켜져 있어 이중 동작했습니다. 방향키가 UI Toolkit 버튼으로 포커스를 옮기고 Enter가 그 버튼을 눌렀습니다. 두 액션의 연결을 끊고 마우스 입력만 남겼습니다.
